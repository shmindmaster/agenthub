# Goal / persistent-objective mechanisms by host — 2026-10-21

Survey of what each coding-agent host on SH-DESKTOP offers for an explicit,
host-understood goal statement: how it is set, where it lives, whether it
survives a session, and how the agent reports progress. Versions verified on
this machine via `--help`/`--version` and the host config directories; thin
spots are cited to web docs.

## Recommended uniform convention

Each program folder gets a **`GOALS.md` beside `STATUS.md`** with: one-sentence
goal, measurable done criteria each labeled with its required rung
(`merged to dev → in main → deployed → production-verified`), non-goals, owner
gates, and check-in cadence. Every host's native mechanism points at it:

- **Claude Code:** `/goal <one-sentence goal; "see GOALS.md for done criteria; report each criterion's rung; append STATUS.md after each step">`.
- **Codex:** `/goal create "…see GOALS.md…"` — survives reboots; `/goal` to inspect on resume.
- **Cursor:** `/goal` if the build exposes it; otherwise a `.cursor/rules` entry naming GOALS.md.
- **All other hosts:** an always-on instruction file (AGENTS.md / CLAUDE.md / GEMINI.md / AGENT.md / .clinerules / devin rules / `.cursor/rules`) saying: *"This session runs program <X>. Read GOALS.md beside STATUS.md before starting; work its items in order; append a rung-labeled line to STATUS.md after each step."* For droid, additionally `droid --append-system-prompt-file GOALS.md`.

This gives parity of outcome (per global policy): the three `/goal` hosts get
self-evaluating loops; the rest get a durable pointer plus STATUS.md discipline.
